# HR ATS Backend v5 — System Documentation (11082025)

Production-ready, Railway-optimized backend for AI-powered resume ingestion, analysis, search, and chat.

Last updated: 2025-08-11

---

## 1) Purpose and Scope

This service ingests resumes (PDF/DOCX/ZIP), stores files in S3/MinIO, extracts text, chunks by section, embeds chunks, and runs a multi-pass agentic LLM pipeline to produce structured facts and summaries. It exposes REST APIs for upload, retrieval, hybrid search, job matching, and streaming RAG chat with citations. It is designed for production on Railway using separate API, worker, and optional beat processes.


## 2) High-level Architecture

- API: Flask + Gunicorn (`app.main:app`), routes in `app/api/routes.py`
- Workers: Celery with Redis broker (`app/workers/celery_app.py`, `app/workers/tasks.py`)
- Database: PostgreSQL (Railway). Uses SQLAlchemy + Alembic migrations. Optional pgvector for vector embeddings.
- Storage: S3-compatible (MinIO). Buckets: `S3_BUCKET` and `S3_BUCKET_TMP`.
- AI/LLM: Ollama service (qwen2.5 family) for extraction and chat; bge-m3 for embeddings.
- Monitoring: Prometheus metrics, health endpoints, status monitoring utilities.
- Deployment: Railway-specific entrypoint (`entrypoint.sh`) and Gunicorn config (`gunicorn.conf.py`).

Data flow
1. Upload: `/api/resumes/upload` → files placed in TMP bucket → promoted to final bucket → DB row created → Celery IO task enqueued
2. IO task: fetch file → text extraction → section-aware chunking → enqueue embedding
3. Embedding task: generate embeddings → write `resume_chunks` → enqueue 3-pass LLM chain
4. LLM passes: map/merge/validate, cascade fallback, QA + scoring → save `resume_facts` snapshot and version history → status to complete
5. Search/match/chat use hybrid FT + vector retrieval with robust fallbacks when vector unavailable

- POST `/api/search` — body: `{ query, page, page_size, top_k? }` with optional `sections` filter in raw JSON; returns chunk hits
- POST `/api/match` — body: `{ job_description, top_k }`; returns aggregated per-resume ranking
- POST `/api/chat` — body: `{ session_id, message, filters? }`; SSE stream with `meta`, `tool` events, and `delta` tokens

Status Monitoring
- GET `/api/status/overview` — system stats
- GET `/api/status/resumes?limit=&offset=` — paginated statuses
- GET `/api/status/resumes/<id>` — detailed status
- GET `/api/status/stuck?minutes=10` — likely stuck items
- GET `/api/status/ready` — ready to analyze
- POST `/api/actions/trigger/<id>` — trigger analysis; `{ force?: bool }`
- POST `/api/actions/auto-recover` — runs automated recovery; `{ dry_run?: bool }`
- POST `/api/actions/trigger-all-ready` — triggers all ready items

## 5) Data Model (SQLAlchemy)
Files: `app/db/models.py`, Alembic in `alembic/versions/*`

Tables
- `resumes` — id (UUID pk), original_filename, mime, size, content_hash, s3_key (nullable, indexed), status, error_message (nullable), created_at, updated_at
- `resume_text` — resume_id (pk, fk), full_text
- `resume_chunks` — id (pk), resume_id (fk, idx), idx, text, embedding (vector or text fallback), section (idx; default "unknown")
- `resume_facts` — resume_id (pk, fk), extracted_json, scores
- `resume_facts_versions` — id, resume_id (idx), pass_no (idx), pipeline, extracted_json, scores, created_at
- `jobs` — id, type, status, error, started_at, finished_at

Vector support detection
- At runtime, `get_embedding_column_type()` and `has_vector_support()` detect if pgvector is installed and the `embedding` column is VECTOR; otherwise fall back to Text storing JSON string vectors. Retrieval functions transparently fallback.

## 6) Processing Pipeline (Celery tasks)
File: `app/workers/tasks.py`

1) `process_resume_io`
- Fetch object from S3, compute hash, deduplicate, extract text (PDF/DOCX with pdfplumber/python-docx; OCR hook ready via Tesseract), write `resume_text`, status → processing
- Ensure `resume_chunks.section` column
- Section-aware chunking (`section_aware_chunks`) → enqueue `embed_chunks_io`

2) `embed_chunks_io`
- Generate embeddings via Ollama bge-m3 with concurrency guard (`OLLAMA_NUM_PARALLEL`)
- Persist chunks: embedding stored as VECTOR or JSON string fallback
- Enqueue `analyze_resume_llm`

3) `analyze_resume_llm` → orchestrates 3-pass chain
- Pass1 (`analyze_resume_pass1_llm`): map-extract subset, merge, validate, short summary, compute base scores; save snapshot + version pass=1; enqueue pass2
- Pass2 (`analyze_resume_pass2_llm`): map-extract full, summaries, QA checks, scores; if low confidence, cascade fallback (`extract_facts_with_cascade`) with larger model → recompute; save snapshot pass=2; enqueue pass3
- Pass3 (`analyze_resume_pass3_llm`): enrich summaries, QA+scores, finalize; save snapshot pass=3; resume status `complete`

Metrics recorded: extract, embed, LLM latency; agent confidence histogram; fallback counter.


## 7) Retrieval & Chat
File: `app/services/retriever.py`

- Full-text: `resume_text.fts` GIN index (created by migration; runtime ensures if missing)
- Vector similarity: pgvector `l2_distance` when available; otherwise graceful fallback that ranks recent chunks with section weightings
- Hybrid advanced search (`hybrid_search_adv`): RRF fusion of vector rank + FT resume rank, optional section filters, MMR selection with diversity; fully works with vector fallback
- Chat (`app/services/llm.py`): RAG stream using qwen2.5 7B; emits SSE `meta`, `tool`, and `delta` events. Citations include resume_id/chunk_idx/section.


## 8) Storage & Buckets
File: `app/services/storage.py`

- `upload_to_tmp`: accepts single files or ZIPs containing PDF/DOCX; size limit via `MAX_FILE_SIZE_MB`; uploads to `S3_BUCKET_TMP`; records original filename in metadata
- `promote_tmp_to_resumes`: copies TMP → final bucket; deletes TMP object; returns final items
- `ensure_buckets_existence`: verifies/creates buckets; API startup logs connectivity checks
- `get_object`: fetches object; returns bytes; raises typed errors for missing keys


## 9) Deployment (Railway)
- Entrypoint: `entrypoint.sh` — prints environment, verifies DB/Redis, sets up Ollama for API role, runs preflight; dispatches by `ROLE` (api|worker|beat)
- API server: Gunicorn (`gunicorn.conf.py`) with Railway-focused tuning (workers, timeouts, access log format, readiness hooks)
- Roles
  - api: Flask app + optional Ollama sidecar bootstrap
  - worker: Celery worker with queues: `io,llm`, prefetch multiplier 4
  - beat: Celery beat (optional). Schedule includes `monitor_resume_status` (1m) and `resume_health_check` (5m)

## 11) Operations: Debug, Recovery, and Cleanup

A. Quick checks
- `/api/debug/config` — validate non-secret config resolved as expected
- `/api/debug/s3test` — list buckets + head target buckets
- `/api/healthz/details` — confirm DB/Redis/S3 reachability

B. Database migrations
- Preferred: POST `/api/debug/migrate` — invokes Alembic upgrade to head
- Fallback: POST `/api/debug/migrate-sql` — adds `s3_key` + `error_message` and sets alembic_version to `20250810_04`

C. Resume pipeline recovery
- GET `/api/status/stuck?minutes=10` — inspect stuck items
- POST `/api/actions/auto-recover` — auto-recover stuck and trigger ready
- POST `/api/actions/trigger/<id>` — trigger specific resume
- POST `/api/actions/trigger-all-ready` — backfill all ready items

D. Orphaned data cleanup (SQL guidance)
- Orphaned chunks: remove rows in `resume_chunks` without a matching `resumes.id`
- Orphaned texts/facts: remove rows in `resume_text`/`resume_facts` without matching resume
- Consider vacuum/analyze after bulk deletes; monitor table sizes (exposed by `resume_health_check` task)

E. Full-text maintenance
- `resume_text.fts` creation and GIN index are handled by migrations and runtime guard. If needed, re-run migration `20250810_00` FT block or refresh FTS with an UPDATE.

F. S3/MinIO cleanup
- TMP bucket should be empty after successful promotions; safe to purge left-over TMP keys older than N hours
- Final bucket: delete objects linked to deleted resumes as part of separate retention job (not included here)

G. Redis/Celery
- If queues back up, consider purging non-critical queues (e.g., `io`) and retriggering ready resumes via API. Ensure broker connectivity and concurrency settings are appropriate for resources.

H. Ollama models
- Ensure `OLLAMA_MODELS` are pulled if required; large models consume RAM/VRAM. Remove unused models to reclaim space.

I. Pgvector enablement
- Migrations attempt to create the `vector` extension with autocommit and retry; when not available, system operates in text-fallback mode. To enable vector later, run `20250810_02` recovery migration; it will attempt column conversion to `VECTOR(1024)`.


## 12) Performance and Tuning
- Gunicorn: `WEB_CONCURRENCY` (default 4), `GUNICORN_TIMEOUT` (120)
- Celery worker: `WORKER_CONCURRENCY` (default 24 in config), `worker_prefetch_multiplier`=4
- Embeddings: `OLLAMA_NUM_PARALLEL` controls in-flight embedding jobs
- Retrieval: `RETRIEVAL_PER_RESUME_LIMIT`, `TOP_K`, context limits affect chat latency
- Large file handling: `MAX_FILE_SIZE_MB` guard


## 13) Security & Reliability
- Secrets via environment variables only
- Error messages for storage/DB surfaced into `resumes.error_message` for observability
- Robust try/except and fallback logic across startup, migrations, embeddings, retrieval, and LLM steps
- Health and metrics endpoints ready for platform probes and dashboards


## 14) Known Limitations
- Local OCR workflow requires `TESSERACT_CMD` and OCR container support
- Vector search quality reduced in fallback mode (no pgvector)
- No built-in retention/GC for S3 and DB beyond monitoring references; operational jobs may be added

## 16) How to Develop Locally (optional)
- Install from `requirements.txt`
